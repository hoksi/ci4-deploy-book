# 3장. php-cli가 막힌 환경 진단하기

## 짐작하지 말고 확인하라

공유 호스팅마다 막아놓은 게 제각각입니다. "이 호스팅사는 이런 식일 것"이라는 선입견으로 작업을 시작하면, 나중에 가서야 막힌 부분을 발견하고 처음부터 다시 설계해야 하는 일이 생깁니다. SSH로 직접 들어가서 **하나씩 실제로 실행해보고 확인하는 것**부터 시작합니다.

## 진단 체크리스트

```bash
ssh your_id@your-host.com

# 1. 기본 셸 환경 확인
pwd
ls -la
echo $SHELL

# 2. PHP CLI
php -v
which php

# 3. Composer
composer --version

# 4. Git
git --version

# 5. 아웃바운드 네트워크 (외부 API 호출이 되는가)
curl -sI https://api.groq.com

# 6. cron 등록 가능 여부
crontab -l
```

이 여섯 가지 결과에 따라 전략이 완전히 달라집니다.

| 확인 항목 | 되는 경우 | 안 되는 경우 |
|---|---|---|
| `php -v` | `php spark migrate` 등 CLI 명령 직접 실행 가능 | 4\~5장의 git/수동 배포 방식 필요 |
| `composer --version` | 서버에서 의존성 설치 가능 | 로컬에서 `vendor/` 통째로 올려야 함 |
| `git --version` | 4장의 git 기반 배포 가능 | SFTP로 파일 하나하나 올려야 함(훨씬 번거로움) |
| 아웃바운드 네트워크 | 외부 API(Groq 등) 호출 가능 | 방화벽 정책 문의 필요 — 이 경우 호스팅 자체를 재검토 |
| `crontab -l` | 정기 작업(백업, 캐시 정리 등) 자동화 가능 | 호스팅사 자체 cron UI(보통 URL 호출 방식)로 대체 |

## 흔한 조합 패턴

1권 13장에서 다룬 cafe24 사례 — **SSH는 되지만 `php` 명령어 자체가 없는** 경우 — 가 대표적이지만, 실제로는 몇 가지 패턴이 더 있습니다.

**패턴 A: SSH + git은 되는데 php-cli만 막힘** (1권에서 다룬 cafe24 사례)
코드 배포는 `git pull`로, DB 작업은 로컬에서 대신 수행하는 전략이 통합니다. 4\~5장에서 다룹니다.

**패턴 B: SSH 자체가 없고 FTP/SFTP만 제공**
git도 못 쓰므로, 로컬에서 변경된 파일만 골라 SFTP로 업로드해야 합니다. 배포 자동화가 훨씬 까다로워지는 경우라, 가능하다면 호스팅 변경을 고려해볼 만합니다.

**패턴 C: php-cli는 되는데 cron/장기 실행 프로세스가 제한적**
큐 워커(백그라운드로 계속 도는 프로세스)를 못 돌리는 경우입니다. 호스팅사의 자체 cron(보통 "특정 URL을 주기적으로 호출"하는 방식)으로 대체해야 합니다.

**패턴 D: 아웃바운드 네트워크 자체가 막혀 있음**
AI API(Groq 등) 호출이 안 되는 치명적인 경우입니다. 이건 설정으로 우회할 방법이 없고, 호스팅사에 문의하거나 다른 호스팅으로 옮기는 수밖에 없습니다.
