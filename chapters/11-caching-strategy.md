# 11장. 캐싱 전략

## File 캐시로 시작해서, 필요할 때 Redis로

CI4는 기본적으로 파일 기반 캐시(`writable/cache/`)를 씁니다. 트래픽이 적거나 서버가 한 대뿐이라면 이것만으로 충분합니다.

```php
// app/Config/Cache.php
public string $handler       = 'file';
public string $backupHandler = 'dummy';   // 1차 핸들러가 실패하면 "캐시 없는 척" 조용히 통과
```

`backupHandler`가 `dummy`인 걸 눈여겨보세요 — Redis 같은 외부 캐시 서버가 죽었을 때, CI4는 에러를 던지는 대신 **캐시가 없는 것처럼 동작**합니다. 캐시 장애가 서비스 전체 장애로 번지지 않게 해주는 중요한 안전장치입니다.

서버가 여러 대(로드밸런서 뒤에 여러 앱 서버)로 늘어나면 파일 캐시로는 부족해집니다 — 서버 A가 캐시한 내용을 서버 B는 모르기 때문입니다. 이 시점에서 모든 서버가 공유하는 Redis로 전환합니다.

```php
public string $handler = 'redis';

public array $redis = [
    'host'     => env('cache.redis.host', '127.0.0.1'),
    'password' => env('cache.redis.password', null),
    'port'     => env('cache.redis.port', 6379),
    'timeout'  => 0,
    'database' => 0,
];
```

전환 자체는 설정 한 줄이고, **애플리케이션 코드(`cache()->get()`, `cache()->save()`)는 전혀 바뀌지 않습니다.** 이게 CI4 캐시 서비스의 핵심 장점입니다 — 핸들러만 교체하면 되도록 설계되어 있습니다.

## 뭘 캐시할지 판단하는 기준

모든 걸 캐시하고 싶은 유혹이 생기지만, 캐시는 "자주 조회되고, 자주 안 바뀌는 데이터"에만 써야 효과적입니다.

| 데이터 | 캐시 적합도 | 이유 |
|---|---|---|
| 게시글 목록(페이지네이션) | 높음 | 조회는 잦고, 새 글은 상대적으로 드묾 |
| 외부 API 응답(날씨, 환율 등) | 높음 | API 호출 자체에 비용/지연이 있고, 결과가 짧은 시간 안에는 안 바뀜 |
| 로그인한 사용자의 알림 개수 | 낮음 | 사용자마다 다르고, 자주 바뀜 — 캐시 적중률이 낮아 오히려 오버헤드 |
| 실시간 채팅 메시지 | 캐시 대상 아님 | 매번 최신이어야 함 |

1권 7장(AI 챗봇)의 웹 검색 결과 캐시가 좋은 예입니다 — 같은 질문이 짧은 시간에 반복되면 외부 검색 API를 또 호출하지 않고 캐시된 결과를 재사용했습니다.

```php
$cacheKey = 'serper_' . md5($query);
$cached   = cache($cacheKey);
if ($cached !== null) return $cached;
// ... API 호출 ...
cache()->save($cacheKey, $result, 600);   // 10분
```

## 캐시 무효화: TTL만으로 충분한가

가장 간단한 전략은 TTL(만료 시간)만 믿는 것입니다 — "10분 지나면 알아서 사라진다." 데이터가 자주 안 바뀐다면 이걸로 충분합니다. 하지만 "**글을 수정했는데 캐시된 옛 내용이 10분 동안 보인다**"가 용납 안 되는 경우엔, 데이터가 바뀌는 시점에 캐시를 직접 지워야 합니다.

```php
public function update(int $id)
{
    $this->model->update($id, [...]);
    cache()->delete('post_' . $id);        // 수정 시점에 바로 무효화
    cache()->delete('posts_list_page_1');  // 목록 캐시도 같이
}
```

캐시 키가 여러 군데 흩어져 있으면 이렇게 "무효화해야 할 키를 빼먹는" 실수가 잦아집니다. 캐시 키 생성 규칙을 한 곳(헬퍼 함수나 서비스 클래스)에 모아두면 이런 실수를 줄일 수 있습니다.

```php
// app/Helpers/cache_helper.php
function post_cache_key(int $id): string
{
    return "post_{$id}";
}
```

## 6장과의 연결 — 캐시 전략이 복잡해질수록 트러블슈팅도 복잡해진다

캐시 레이어를 늘릴수록(File → Redis, 수동 무효화 로직 추가) 6장에서 다룬 "캐시 때문에 반영이 안 되는" 문제가 날 가능성도 같이 늘어납니다. 캐시를 도입할 때는 **그 캐시를 강제로 지우는 방법**(관리자 페이지의 "캐시 초기화" 버튼, 또는 `php spark cache:clear`)도 같이 마련해두세요.

## 체크리스트

- [ ] `backupHandler`가 `dummy`로 설정되어, 캐시 서버 장애가 서비스 장애로 번지지 않는가
- [ ] 캐시 적용 대상이 "자주 조회되고 자주 안 바뀌는" 기준에 맞는지 점검했는가
- [ ] 데이터가 변경되는 지점에서 관련 캐시 키를 함께 무효화하고 있는가
- [ ] 캐시를 통째로 초기화할 수 있는 수단이 운영 환경에 마련되어 있는가
