# 6장. 캐시와 OPcache 트러블슈팅

## "분명히 고쳤는데 그대로다"

배포하고 나서 가장 당황스러운 순간은, 코드를 분명히 고쳤고 서버에 배포도 됐는데 브라우저에서는 여전히 예전 화면이 보일 때입니다. 범인 후보가 너무 많다는 게 문제입니다 — OPcache, realpath 캐시, CI4 자체 캐시, 리버스 프록시, 브라우저 캐시, 심지어 **캐시가 아닌 다른 문제**까지. 이 장은 그 후보들을 순서대로 좁혀가는 절차를 다룹니다.

## 진단 순서: 바깥에서 안으로

바깥쪽(브라우저)부터 안쪽(PHP 엔진)으로 하나씩 제거해 나가는 게 효율적입니다. 안쪽 원인을 먼저 의심하면, 사실은 그냥 브라우저 캐시였던 걸 가지고 몇 시간을 날릴 수 있습니다.

### 1단계: 브라우저 캐시부터 제외한다

```bash
curl -I -H "Cache-Control: no-cache" https://your-domain.com/path
```

시크릿/프라이빗 모드로 열어보거나, 강력 새로고침(Ctrl+Shift+R)으로 먼저 확인합니다. 이것만으로 해결되면 범인은 브라우저지, 서버가 아닙니다.

### 2단계: 배포 자체가 제대로 됐는지 확인한다

가장 흔하면서 제일 허탈한 원인입니다. **고친 파일이 실제로 서버에 올라갔는지**부터 확인하세요.

```bash
ssh your_id@your-host.com "md5sum app/Controllers/YourController.php"
md5sum app/Controllers/YourController.php   # 로컬
```

두 값이 다르면 캐시 문제가 아니라 **배포 자체가 실패했거나 덜 된 것**입니다. 4장의 `git log --oneline -1`을 서버에서 실행해 배포된 커밋이 맞는지도 같이 확인하세요.

### 3단계: OPcache를 의심한다

PHP의 OPcache는 컴파일된 PHP 코드를 메모리에 캐시해서 성능을 높입니다. `opcache.validate_timestamps`가 꺼져 있거나, TTL이 길게 잡혀 있으면 **파일을 고쳐도 OPcache가 예전 컴파일 결과를 계속 씁니다.**

```bash
php -i | grep opcache.validate_timestamps
php -i | grep opcache.revalidate_freq
```

공유 호스팅에서는 이 값을 직접 바꿀 권한이 없는 경우가 많습니다. 대신 OPcache를 초기화하는 작은 스크립트를 하나 만들어두면 유용합니다.

```php
<?php
// _opcache_reset.php — 배포 후 한 번 열어주고 바로 삭제
if (function_exists('opcache_reset')) {
    opcache_reset();
    echo 'OPcache reset 완료';
} else {
    echo 'OPcache 사용 안 함';
}
```

**이 파일은 사용 후 반드시 삭제하세요** — 누구나 접근해서 서버의 OPcache를 계속 초기화시킬 수 있는 길을 열어두는 거라, 띄워두는 시간이 길어질수록 위험합니다.

### 4단계: realpath 캐시를 의심한다

PHP는 파일 경로 조회 결과도 캐시합니다(`realpath_cache_size`, `realpath_cache_ttl`). 파일을 새로 만들거나 이름을 바꾼 경우(내용만 수정한 게 아니라) 이 캐시 때문에 PHP가 여전히 옛 경로 정보를 참조할 수 있습니다. TTL이 지나면 자연히 해소되지만(기본값은 보통 120초), 그 사이에 "방금 고쳤는데 왜 안 되지"라고 헷갈릴 수 있습니다.

### 5단계: CI4 자체 캐시를 의심한다

CI4의 `cache()` 서비스로 뷰나 쿼리 결과를 캐시해뒀다면, 코드가 아니라 **캐시된 데이터 자체**가 예전 내용을 들고 있을 수 있습니다.

```bash
php spark cache:clear
```

php-cli가 막혀 있다면, 2단계에서 만든 것과 비슷하게 `cache()->clean()`을 호출하는 임시 스크립트를 하나 만들어 쓰고 지우면 됩니다.

### 6단계: 리버스 프록시/CDN 캐시를 의심한다

Nginx나 Cloudflare 같은 CDN을 앞에 뒀다면, 그쪽이 응답을 캐시하고 있을 수 있습니다. 9장에서 다루는 Nginx 설정에서 `proxy_cache` 관련 지시어가 있는지, Cloudflare라면 대시보드에서 "Purge Cache"를 해봤는지 확인하세요.

## 캐시가 아닐 수도 있다는 걸 염두에 두세요

여기까지 다 확인했는데도 안 바뀐다면, **애초에 캐시 문제가 아닐 가능성을 진지하게 고려해야 합니다.** 흔한 함정은 `.env`의 값이 예상과 다른 경우입니다 — 예를 들어 `app.baseURL`이나 DB 접속 정보가 운영과 로컬이 미묘하게 다른데, 겉보기엔 "똑같은 페이지가 계속 보이는" 증상으로 나타나서 캐시처럼 오해하기 쉽습니다.

실제로 이런 사례가 있었습니다 — 배포 후 분명히 새 코드가 올라갔는데 화면이 안 바뀌어서, OPcache·realpath 캐시·CI4 캐시까지 전부 의심하고 리셋 스크립트를 몇 개나 만들어 테스트했지만 전혀 해결이 안 됐습니다. 몇 시간을 캐시 레이어에서 헤맨 끝에, 원인은 캐시가 아니라 **`.env`에 박혀 있던 설정값 하나**였습니다. 캐시를 의심하는 동안 정작 제일 먼저 확인했어야 할 "지금 어떤 설정값을 읽고 있는가"는 뒤로 미뤄뒀던 겁니다.

교훈은 단순합니다 — **캐시 레이어를 하나씩 제거해 나가는 절차와 별개로, "혹시 그냥 설정값이 틀린 건 아닌가"를 항상 체크리스트 맨 위에 두세요.** 이색적인 원인을 찾아 헤매기 전에, 평범한 원인부터 배제하는 게 결국 더 빠릅니다.

## 체크리스트

- [ ] 브라우저 캐시부터 배제했는가 (시크릿 모드로 확인)
- [ ] 고친 파일이 실제로 서버에 배포됐는지 `md5sum`/`git log`로 확인했는가
- [ ] OPcache, realpath 캐시, CI4 캐시, 리버스 프록시 캐시를 순서대로 배제했는가
- [ ] 여기까지도 해결 안 됐다면 `.env`/설정값부터 다시 확인했는가

2부를 여기서 마칩니다. 3부에서는 공유 호스팅의 제약을 벗어나, VPS/클라우드로 확장할 때 필요한 것들을 다룹니다.
